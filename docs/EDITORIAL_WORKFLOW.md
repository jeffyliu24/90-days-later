# 编辑与自动化工作流

## 原则

自动化负责节省搜集和整理时间，人类负责承担当众推荐的责任。

机器可以：

- 检索候选与异常 star 增长
- 保存 GitHub 和公开数据快照
- 标注 30/90/180/365 天复查窗口
- 生成来源清单、指标表和初稿
- 根据已批准内容生成多平台格式

机器不可以：

- 自动授予 A 级
- 把无法观察的企业使用写成事实
- 删除表现不好的 cohort 成员
- 在没有人类批准时对外发布
- 为凑频率降低证据标准

## 内容状态

```text
candidate
  → researched
  → draft
  → review
  → approved
  → scheduled
  → published
  → due_for_recheck
```

只有 `approved` 内容可以填写 `publish_at`。发布动作只能读取同时满足以下条件的文件：

- `status` 为 `approved` 或 `scheduled`
- `approved_by` 不为空
- 自动校验通过
- `publish_at` 已到达

## 推荐周节奏

### 周二 09:15：候选扫描

自动任务生成不超过 5 个候选，优先级依次为：

1. 接近 T+90 的既有 cohort
2. 接近 T+180 的既有 cohort
3. 评级可能发生变化的项目
4. 新出现的爆发项目

输出必须包含选择理由、反对理由、可用数据和缺失数据。没有足够好的候选时允许输出“本期不建议发布”。

### 周二至周三：人工选题

编辑选择 1 个主报告和最多 1 个轻量更新。未选择的候选进入 backlog，不自动变成稿件。

### 周四：主报告

使用 `content/templates/project-review.md`。至少核验项目仓库、发行说明、安装路径和一项独立采用证据。

### 周日：可选轻量内容

只发布以下内容之一：

- 一张前后对比图
- 某个评级变化及原因
- 新的维护、许可或迁移事件
- 下周复查预告

## 审核清单

- [ ] 项目身份、仓库迁移和官方关系已核验
- [ ] hype date 有数据和事件背景
- [ ] 当时与现在使用同口径指标
- [ ] 自动化账号和机器人活动已单列
- [ ] star 没有被写成真实用户数量
- [ ] 采用证据至少来自一个独立下游
- [ ] 学习价值与采用信心分别评级
- [ ] A 级通过全部硬门槛
- [ ] 风险、反证和未知项已写出
- [ ] 主要结论都有可点击来源
- [ ] `approved_by` 和 `publish_at` 已填写

## 前后对比的固定叙事

每篇内容保持同一顺序，方便读者形成判断习惯：

1. **一夜爆火**：什么事件带来关注？
2. **当时承诺**：项目声称解决什么问题？
3. **时间过去**：30/90/180 天发生了哪些可验证变化？
4. **留下什么**：代码、维护者、用户、集成还是只有 star？
5. **今天怎么选**：谁适合，谁不适合，替代与退出路径是什么？
6. **能学什么**：列出三项可迁移的技术或产品判断。

## 视觉与视频

### 默认：图表与信息卡

每个主报告生成：

- 1 张封面：项目名、hype date、当前阶段、总评级
- 1 张时间线：日/周 star 速度与 release 事件
- 1 张“当时 vs 现在”表
- 1 张五维雷达或条形图
- 1 张适合/不适合与风险卡

### 视频触发条件

满足任意一项才制作短视频：

- 有值得展示的真实操作变化
- 90 天内发生重大转向、合并、归档或许可变化
- 获得维护者回应
- 图表包含清晰的反转故事
- 已有报告表现显著高于栏目中位数

建议第一个月不做视频。第二个月开始，每月把最强的一篇改成 45–90 秒视频，复用已有图表和文字，不建立独立的视频选题流水线。

## 渠道角色

- GitHub：完整数据、方法、报告和更正历史
- 公众号：完整中文复盘
- 小红书：5–8 张信息卡与结论
- X：一张核心图、英文摘要和维护者沟通

先维护一个 canonical Markdown 文件，再由它生成各渠道版本。
